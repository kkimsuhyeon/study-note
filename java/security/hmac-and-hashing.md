# HMAC과 해시 — 같은 입력을 비교하는 값과 복호화의 차이

> **한 줄 요약:** 해시는 입력을 요약한 값이고, HMAC은 비밀 키를 함께 사용한 인증 코드다. 원문을 되돌리는 암호화와 달리, 같은 조건으로 다시 계산해서 비교한다.

## 1. 언제 쓰나

예약 요청이 재전송됐을 때 입력이 같은지 비교하거나, 메시지가 공유 비밀 키를 가진 쪽에서 만들어졌는지 확인할 때 쓴다. 단순히 새 식별자가 필요하면 UUID나 난수를 쓰는 편이 목적에 맞다.

| 방식 | 입력 | 주된 목적 | 원문 복원 |
| --- | --- | --- | --- |
| SHA-256 같은 해시 | 메시지 | 내용 요약·변경 비교 | 복호화 연산 없음 |
| HMAC-SHA256 | 비밀 키 + 메시지 | 키 기반 메시지 인증·비교 | 복호화 연산 없음 |
| 암호화 | 키 + 평문 + 알고리즘별 추가 값 | 내용을 숨기고 나중에 복원 | 올바른 키 등으로 가능 |
| 난수 토큰 | 안전한 난수 | 예측하기 어려운 식별·접근 값 | 원문이라는 개념이 없음 |

HMAC의 정확한 이름은 **해시 기반 메시지 인증 코드**다. 단순히 `SHA256(키 + 메시지)`를 직접 만드는 것과는 다르다. Java가 제공하는 `Mac`을 사용한다. [Java 25 Mac](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/javax/crypto/Mac.html)

## 2. Java에서 만들기

다음은 호출자가 유효한 키와 값을 전달하는 학습용 예시다. 운영용 키는 소스 코드에 적지 않는다.

```java
import java.nio.charset.StandardCharsets;
import java.security.GeneralSecurityException;
import java.util.HexFormat;
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;

public class MessageHasher {
    public String hash(byte[] secret, String purpose, String message)
            throws GeneralSecurityException {
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(secret, "HmacSHA256"));
        byte[] input = (purpose + "\n" + message)
                .getBytes(StandardCharsets.UTF_8);
        return HexFormat.of().formatHex(mac.doFinal(input));
    }
}
```

- `getBytes(UTF_8)`: 문자열을 일정한 규칙의 바이트로 변환한다.
- `doFinal(...)`: HMAC을 계산해 바이트로 반환한다.
- `HexFormat`: 바이트를 16진수 문자열로 표현한다. **암호화·복호화가 아니다.**
- `purpose`: `payload`, `cache`처럼 개발자가 정한 용도 구분값이다. 동일한 메시지를 다른 용도로 쓰더라도 입력을 구분한다. 예시에서는 줄바꿈 없는 고정된 용도명을 쓴다고 가정한다.

`Mac`은 계산 상태를 가지므로 위 예시는 호출마다 새로 만든다. 여러 요청이 같은 객체를 동시에 변경하는 문제를 피하는 방식이다.

## 3. 같은 메시지면 같은 값인가?

**알고리즘·키·입력 바이트가 모두 같으면 같은 값**이다. 위 코드에서는 purpose도 입력의 일부다.

```text
같은 키 + payload + 같은 메시지 → 같은 결과
다른 키 또는 다른 purpose 또는 다른 메시지 → 보통 다른 결과
```

출력 길이는 유한하므로 서로 다른 입력이 같은 값이 되는 충돌 가능성을 수학적으로 0이라고 말할 수는 없다. HMAC을 DB의 완전한 유일성 보장 장치와 동일시하지 않는다.

### purpose는 어디서 실제로 일하나 — 이름 공간(domain separation)

`hash(purpose, value)`가 여러 호출자의 공용 메서드일 때, purpose는 용도별 값이 **구조적으로 겹칠 수 없게** 하는 이름 공간이다. 같은 키에 용도 접두사를 붙여 입력 영역을 나누는 이 방식을 **domain separation**이라 하고, `HMAC(key, "A\n…")`와 `HMAC(key, "B\n…")`는 서로 다른 의사난수 함수처럼 동작한다. 더 강한 대안은 **key separation** — 용도마다 키 자체를 따로 두거나 마스터 키에서 HKDF의 `info`로 용도별 키를 파생하는 것이다. 키 하나가 새도 다른 용도까지 번지지 않는 대신 키 관리가 늘어난다.

| 상황 | purpose 없이 `hash(value)` | purpose 있음 |
| --- | --- | --- |
| 한 컬럼에 두 종류 subject(세션·IP)가 공존 | "입력 형식이 다르니 안 겹치겠지"라는 우연에 의존 | 겹칠 수 없음 |
| 같은 원문(예: 소유자 값)을 훗날 새 용도로 또 해시 | 같은 값이 두 테이블에 → 테이블 간 연결, 공개 토큰이 내부 키가 되는 사고 | 용도마다 다른 값 |
| IP 해시의 날짜 회전 | 별도 규칙 필요 | purpose에 날짜를 넣으면 끝 (`ip-rate:<UTC 날짜>`) |
| 입력이 이미 새 난수 UUID(소유자 식별값) | 차이 없음 | **차이 없음** — 형식 통일 의미만 |

⚠️ 마지막 행이 함정이다. 난수 입력에 purpose를 붙인 호출을 보고 "purpose가 뭔가 보안을 더하나?"라고 읽으면 안 된다. 그 호출은 다른 호출자와 규약을 맞추는 것이고, purpose가 실제로 일하는 곳은 **같은 원문이 두 용도로 쓰이거나 한 컬럼에 두 용도가 공존하는** 자리다. `"\n"` 구분자도 같은 맥락 — `"ab"+"c"`와 `"a"+"bc"`가 같은 입력이 되는 모호함을 purpose에 줄바꿈이 없다는 규약으로 없앤다.

## 4. payload와 fingerprint는 알고리즘 이름이 아니다

둘 다 개발자가 붙인 **비교 목적**이다. 예를 들어 예약 서비스에서 다음처럼 정할 수 있다.

| 값 | 포함할 정보 | 비교하는 상황 |
| --- | --- | --- |
| 요청 내용 해시(payload) | 예약자 이름·상품·날짜·수량 | 같은 중복 방지 키로 다른 요청을 보냈는지 |
| 계산 조건 지문(fingerprint) | 상품·날짜·수량·요금 규칙 버전 | 이전에 계산한 견적을 재사용할 수 있는지 |

이름을 바꿔도 견적은 같지만, 요청 내용은 달라질 수 있다. 어떤 필드를 포함할지는 이 업무 규칙으로 결정한다. 공통 `inputFields()`는 두 계산에 필요한 필드를 모으는 보조 메서드일 뿐, 스스로 해시를 계산하거나 데이터를 저장하지 않는다.

UUID 기반 중복 방지 키와도 다르다. UUID는 클라이언트가 **같은 작업의 재전송**에 재사용하는 식별자이고, payload 해시는 그 키로 보낸 **내용도 같은지** 확인하는 데 사용할 수 있다.

### 같은 멱등 키를 찾은 뒤 작업 종류와 본문도 비교하는 이유

예를 들어 `(owner, key)`로 요청 기록을 조회하는 예약 API라면, 이전 기록은 "이 사용자의 가장 최근 요청"이 아니라 **이 사용자가 이 키로 보낸 요청**이다. 같은 키가 발견됐다는 것만으로 같은 작업이라고 확정하지 않고, 기록의 `operation`(예: `POST /reservations`)과 정규화한 본문의 해시를 비교한다. `operation`은 작업 종류이며 `pending`·`completed` 같은 처리 상태와 다르다.

| 같은 owner·key로 다시 보낸 내용 | 처리 예시 |
| --- | --- |
| 예약 생성 + 이전과 같은 입력 | 기존 예약을 찾아 반환 |
| 예약 생성 + 수량 등 입력 변경 | 키를 다른 내용에 재사용했으므로 충돌 오류 |
| 이전에는 예약 취소, 이번에는 예약 생성 | 키를 다른 작업에 재사용했으므로 충돌 오류 |

본문 변경을 감지하지 않으면, 사용자가 수량을 바꿨는데도 서버가 이전 수량의 예약을 반환할 수 있다. 새 작업에는 새 키를 발급하고, 응답 유실 등으로 **같은 작업을 재전송할 때는 기존 키를 유지**한다. Stripe도 같은 멱등 키의 입력 매개변수가 기존 요청과 다르면 오류로 처리한다. 구체적인 키 범위·오류 상태 코드는 API 계약에 따른다. [Stripe — Idempotent requests](https://docs.stripe.com/api/idempotent_requests)

### 같은 해시 도구를 여러 곳에서 쓰는 이유

해시 계산이라는 기술은 같아도 **무엇을 식별·비교하는가**가 다를 수 있다.

```text
방문자 식별값 → 이 예약은 누구의 것인가?
요청 내용 해시 → 같은 키로 제출한 내용도 같은가?
견적 조건 지문 → 이전 견적을 재사용할 수 있는가?
사용량 집계 키 → 누구의 요청 횟수를 누적할 것인가?
```

방문자 식별값을 세션에 한 번 넣어 재사용하면 예약 여러 개가 같은 소유자 값을 가질 수 있다. 새 요청 내용 해시는 입력마다 계산하므로 **같은 방문자라도 예약 내용을 바꾸면 달라진다.** Controller가 세션 담당 객체에 식별값을 요청하고, Service가 입력 해시를 계산하더라도 같은 일을 중복한 것이 아니다.

소유자 식별과 집계 키의 목적을 분리하려고 이미 만든 식별값을 다시 HMAC 입력으로 사용할 수도 있다. 이것은 설계 선택이며, **식별자는 반드시 두 번 해시해야 한다는 규칙은 없다.** 식별값 자체는 난수로 만드는 선택도 가능하다. 세션 관리는 [HttpSession](../spring/http-session.md)을 참고한다.

## 5. ⚠️ Java 값이 같아 보여도 바이트가 다를 수 있다

```json
{"quantity":2,"date":"2030-05-10"}
```

```json
{"date":"2030-05-10","quantity":2}
```

JSON 객체로는 같은 내용이어도 문자열 순서가 다르다. 해시 입력에서는 키 순서·공백·null 처리·enum 표기·시간 표기를 통일해야 한다. 예를 들어 `TreeMap`으로 키 순서를 고정해도 중첩 객체나 숫자 표현까지 자동으로 정규화되는 것은 아니다.

타입을 `String`에서 enum으로 바꿀 때도 `"female"`이 `"FEMALE"`로 바뀌면 해시가 달라진다. 리팩터링 전후의 고정 입력에 대해 **기존 해시 값과 같은지** 테스트하면 이런 변화를 발견할 수 있다.

**복호화할 수 없다는 말이 모든 정보를 숨겨 준다는 뜻은 아니다.** 일반 해시는 생일처럼 후보가 적은 값을 대입해 추측할 수 있다. HMAC은 키를 모르는 사람의 계산을 어렵게 하지만, 키가 노출되거나 같은 값의 반복이 보이는 문제까지 없애 주지는 않는다. 비밀번호 저장 목적은 별도의 [PasswordEncoder 노트](./password-encoding.md)를 따른다.

## 6. 역할별로 "왜 이 방식인가" — 저장 위치와 원문의 추측 가능성으로 갈린다

4절의 값들을 로그인 없는 예약 API 하나에 놓고, 각 값이 **어디에 저장되고 원문이 얼마나 추측 가능한가**를 보면 HMAC을 쓸 자리와 안 써도 되는 자리가 갈린다.

| purpose | 원문(value) | 저장 위치 | 왜 HMAC인가 |
| --- | --- | --- | --- |
| `owner` | 새 난수 UUID | 세션 속성 + 예약 행의 소유자 컬럼 | 원문이 이미 난수라 보안상 이득은 없다. 다른 해시 컬럼과 형식(64자 hex)을 맞추는 의미뿐 |
| `payload` | 정규화 JSON(예약자 이름·전화번호 포함) | 멱등 키 테이블 | 전화번호처럼 후보가 1억 개 정도인 값이 섞이면 일반 해시는 전수 대입으로 복원된다 |
| `fingerprint` | 정규화 JSON(상품·날짜·수량) + 요금 규칙 버전 | 예약 행의 캐시 키 컬럼 | 같은 이유. 버전을 넣어 규칙이 바뀌면 캐시가 자동 무효화 |
| `session-rate` | 소유자 식별값 | 한도 테이블 | 한도 테이블만 유출돼도 예약 소유자와 이어지지 않게 한 번 더 감싼다 |
| `ip-rate:<UTC 날짜>` | 클라이언트 IP | 한도 테이블 | IPv4는 2^32개뿐이라 일반 해시는 무력. 날짜를 purpose에 넣어 **같은 IP도 날마다 다른 값** → 여러 날에 걸친 추적 불가 |

**HMAC이 아닌 일반 SHA-256으로 충분한 자리**도 있다. `(소유자 + ":" + 멱등 키)`를 SHA-256으로 돌려 앞 8바이트를 advisory lock 키로 쓰는 경우다. 저장하지 않고 트랜잭션 안에서만 쓰며, 목적이 직렬화뿐이라 비밀성이 필요 없다 → [advisory lock](../../database/postgres-advisory-lock.md). 한도 버킷을 소비하는 순서·잠금은 → [Rate Limiting](../../infra/rate-limiting.md).

**세션에 두는 해시는 소유자 식별값 하나다.** payload·fingerprint·rate 해시는 매 요청의 본문·IP·시각에서 다시 계산해 DB 값과 비교하면 되므로 세션에 둘 이유가 없고, advisory lock 키는 어디에도 저장하지 않는다. 소유자 식별값은 **세션 ID로 계산하지 않고 세션 속성으로 저장**한다 — `hash(세션 ID)`였다면 세션 고정 방지로 ID를 바꾸는(`changeSessionId`) 순간 소유권과 한도 카운트를 잃지만, 속성은 ID가 바뀌어도 따라간다. 두 사용자가 같은 멱등 키 UUID를 써도 기본 키가 `(owner, idempotency_key)` 조합이면 소유자별로 격리된다.

💡 **난수 기반 식별자는 충돌이 아니라 유출을 걱정한다.** `SecureRandom` UUID(2^122)는 세션 10억 개에서도 충돌 확률이 10^-19 수준이라 유일 제약·재시도 코드가 필요 없다. 남이 내 식별값을 얻는 길은 추측이 아니라 세션 쿠키 탈취이고, 그건 해시 설계가 아니라 쿠키 속성(`Secure`·`HttpOnly`·`SameSite`)의 영역이다([세션과 쿠키](../../infra/network/sessions-and-cookies.md)).

💡 **같은 세션이면 식별값은 항상 같다 — 한 번만 쓰기(set-once).** 조회는 "있으면 그 값", 저장은 "없을 때만"으로 짜면 세션이 사는 동안 값이 바뀌지 않는다. 값이 달라지는 건 세션이 **새로** 생길 때(쿠키 삭제·만료)뿐이다 — Spring Session은 만료된 ID가 다시 와도 재사용하지 않고 새 ID를 발급한다(세션 고정 방지). 그러니 **자원 수명(생성 후 N일) ≤ 세션·쿠키 수명(마지막 활동 후 N일)**으로 맞춘다. 마지막 활동은 생성보다 늦거나 같으므로 살아 있는 자원이 소유자를 먼저 잃는 일이 없다.

### ⚠️ 키 교체·리네이밍

- **키를 바꾸면** payload·fingerprint·rate 해시가 전부 달라진다. 이미 저장된 소유자 해시는 그대로라 소유권은 유지돼도, 같은 요청의 재전송이 "다른 내용"으로 판정되고 캐시는 전부 miss, 한도 카운터는 0부터 시작한다. 키 교체는 배포 이벤트로 다룬다.
- purpose 문자열과 JSON 필드 이름은 사실상 **DB 저장 포맷**이다. 리네이밍 한 번에 기존 행 전부가 미아가 되므로, 고정 입력 → 기대 hex 값을 박아 둔 테스트(golden test)를 남기고 리팩터링 전후로 돌린다. 5절의 `"female"` → `"FEMALE"` 함정이 바로 이것.

💡 **방식 선택 기준 — 원문이 어디에 놓이고 얼마나 추측 가능한가.** (1) DB에 저장되고 원문이 생일·IP처럼 후보가 적다 → HMAC(키 없이는 대입 불가). (2) 저장하지 않고 정수 키만 잠깐 필요하다 → 일반 해시로 충분. (3) 원문이 이미 안전한 난수다 → 해시가 보안을 더하지 않으니, 형식 통일이 목적이면 그렇게 적어 둔다. (4) 시간이 지나며 연결되면 안 되는 값(IP)은 날짜 같은 회전 요소를 purpose에 넣는다.

### 해시만 있는 DB를 디버깅할 때 — 되돌리지 말고 "다시 계산해서 대조"

DB를 열어 보면 해시 열은 의미 없는 16진수뿐이라 "아무것도 못 본다"고 느끼기 쉽다. 해시는 되돌릴 수 없지만, **후보 원문을 같은 방식으로 다시 계산해 일치하는지**는 볼 수 있다. 서버가 요청마다 하는 일도 정확히 이것이다(요청에서 IP를 받아 해시 → 같은 행 조회).

```js
// 로컬 개발 키로 "이 버킷 행이 127.0.0.1 것인가?" 확인 (키는 출력하지 않는다)
const h = (purpose, value) => crypto.createHmac('sha256', Buffer.from(key, 'utf8'))
    .update(purpose + '\n' + value, 'utf8').digest('hex');
h('ip-rate:2026-10-08T00:00:00Z', '127.0.0.1')   // → DB의 subject_hash와 같으면 그 IP의 칸
```

- 대조하려면 **키·purpose·구분자·값의 정규화(IPv6 표기 등)**를 서버와 바이트 단위로 똑같이 맞춰야 한다. 하나라도 다르면 전혀 다른 값이 나온다.
- 같은 이유로 **키 없이 DB만 유출되면 이 대조가 불가능**하다 — 이것이 IP에 일반 해시가 아니라 HMAC을 쓰는 이유다.
- 해시가 아닌 열(입력 JSON처럼 나중에 원문이 필요한 값)은 평문으로 남는다. "해시했으니 개인정보가 없다"가 아니라 **열마다** 확인한다.
