# AOP 개념 — 횡단 관심사를 모듈화하는 패러다임

> **한 줄 요약**: AOP(Aspect-Oriented Programming)는 로그·트랜잭션 같은 **횡단 관심사(cross-cutting concerns)**를 **애스펙트**라는 모듈로 분리하는 패러다임이다. 스프링은 AspectJ의 **문법만 차용**하고 실제로는 **프록시 방식(런타임 위빙)**으로 동작한다 — 따라서 조인 포인트가 **메서드 실행으로 제한**되고, **스프링 빈에만** 적용할 수 있다. ⚠️ 프록시 제약의 근본 원인은 "빈 등록 이후라서"가 아니라 **메서드 오버라이딩 개념으로 동작하기 때문**이다.

관련 노트: [@Aspect AOP](./aspect-aop.md) (직전 챕터 — `@Aspect`가 어떻게 Advisor로 변환되는지) · [빈 후처리기](./bean-post-processor.md) (`AnnotationAwareAspectJAutoProxyCreator`의 프록시 생성 메커니즘) · [ProxyFactory](./proxy-factory.md) (`Advisor = Pointcut + Advice`의 출처) · [동적 프록시](./dynamic-proxy.md) (JDK 동적 프록시 vs CGLIB 기반 기술) · [프록시/데코레이터 패턴](./proxy-decorator-pattern.md) (프록시 개념의 출발점) · [ThreadLocal](../concurrency/thread-local.md) (Ch.2 — 트랙 시작) · [@Transactional](../spring/transactional.md)·[Spring Cache](../spring/spring-cache.md)·[메서드 보안](../security/method-security.md) (AOP 위에서 동작하는 실무 어노테이션들)

## 0. 출발점 — 부가 기능 적용의 근본 문제

Ch.4~8에서 프록시 기술을 점진적으로 발전시켜 `@Aspect`까지 도달했다. 하지만 이 기술들이 **왜 필요한지** — 즉 OOP만으로는 해결할 수 없는 문제가 무엇인지를 정리하는 챕터가 이번 Ch.9다. 실습 코드 없이 **개념과 용어를 잡는 이론 챕터**이다.

### 핵심 기능 vs 부가 기능

```
애플리케이션 로직
├── 핵심 기능: 객체의 고유 기능 (예: OrderService의 주문 로직)
└── 부가 기능: 핵심 기능을 보조 (예: 로그 추적, 트랜잭션)
    → 단독 사용 불가, 항상 핵심 기능과 함께 사용
```

### OOP로 부가 기능을 적용할 때의 4가지 문제

| # | 문제 | 구체 상황 |
|---|------|----------|
| 1 | 적용할 때 **반복이 많다** | 100개 클래스에 동일한 `try-catch-finally` 로그 코드 추가 |
| 2 | 여러 곳에 퍼져서 **중복 코드** 발생 | 유틸리티 클래스로 빼도 호출 코드가 100곳에 남음 |
| 3 | 부가 기능 **변경 시 수정이 많다** | 로그 포맷 변경 → 100곳 수정 |
| 4 | **적용 대상 변경 시에도 수정이 많다** | "서비스 계층에만 적용하자" → 나머지 100곳에서 제거 |

핵심: **변경 지점이 하나로 모듈화되지 않는다**. 소프트웨어 개발에서 변경 지점은 하나가 될 수 있도록 모듈화되어야 하는데, 부가 기능처럼 **애플리케이션 전반에 걸치는 로직**은 일반적인 OOP 방식으로는 해결이 어렵다.

## 1. 애스펙트(Aspect)와 AOP

### 횡단 관심사 (Cross-Cutting Concerns)

부가 기능이 여러 클래스·계층을 **가로질러(횡단)** 퍼져있는 것을 **횡단 관심사**라 한다. 로그, 트랜잭션, 보안 검사 등이 대표적이다.

```
Controller ──────── Service ──────── Repository
    │ 로그              │ 로그              │ 로그
    │ 트랜잭션           │ 트랜잭션           │
    │ 보안              │                  │
    ↓                  ↓                  ↓
    ─────────── 횡단 관심사 ───────────────
```

### 애스펙트 = 부가 기능 + 적용 대상을 하나의 모듈로

누군가는 이 문제를 해결하기 위해 오랜 기간 고민한 끝에, 부가 기능을 핵심 기능에서 **분리**하고 한 곳에서 관리하도록 했다. 그리고 해당 부가 기능을 **어디에 적용할지 선택하는 기능**도 만들었다. 이렇게 둘을 합해서 하나의 모듈로 만든 것이 **애스펙트(Aspect)**이다.

- **어드바이스(Advice)** — 부가 기능 로직 그 자체
- **포인트컷(Pointcut)** — 어디에 적용할지 정의

이전 챕터에서 배운 `@Aspect`가 바로 그것이고, **어드바이저(Advisor)** 역시 어드바이스 + 포인트컷을 가지고 있으므로 개념상 하나의 애스펙트이다.

이렇게 애스펙트를 사용한 프로그래밍 방식을 **AOP(Aspect-Oriented Programming, 관점 지향 프로그래밍)**이라 한다.

> AOP는 OOP를 **대체**하기 위한 것이 아니라, 횡단 관심사를 깔끔하게 처리하기 어려운 OOP의 부족한 부분을 **보조**하는 목적으로 개발되었다.

### AOP가 쓰이는 대표 예시

강의에서 언급된 활용처 — 전부 이 볼트의 실무 노트들과 1:1로 대응된다:

- 트랜잭션 → [@Transactional](../spring/transactional.md)
- 성능 최적화(캐싱) → [Spring Cache](../spring/spring-cache.md)
- 보안 검사 → [메서드 보안](../security/method-security.md)
- 모니터링 및 로깅 → Ch.1~2의 `LogTrace`가 바로 이것

## 2. AOP 적용 방식 — 위빙 시점 3가지

부가 기능 로직을 실제 로직에 추가하는 것을 **위빙(Weaving)**이라 한다 (옷감을 짜다, 직조하다 — 애스펙트와 실제 코드를 연결해서 붙이는 것).

### 세 가지 위빙 시점 비교

| 시점 | 동작 | 대상 코드 변화 | 필요 도구 |
|------|------|---------------|-----------|
| **컴파일 시점** | `.java` → `.class` 만들 때 바이트코드에 부가 기능 삽입 | 실제 코드에 부가 기능 호출 코드가 **포함됨** | AspectJ 전용 컴파일러 |
| **클래스 로딩 시점** | `.class`를 JVM 클래스 로더에 올릴 때 바이트코드 조작 | 실제 코드에 부가 기능 호출 코드가 **포함됨** | `java -javaagent` 옵션 (로드 타임 위빙) |
| **런타임 시점** ⭐ | `main()` 실행 후, 프록시를 통해 부가 기능 적용 | 실제 코드는 **그대로 유지**, 프록시가 감쌈 | **스프링 AOP** (스프링만 있으면 됨) |

### 각 시점의 단점

- **컴파일 시점**: AspectJ가 제공하는 특별한 컴파일러가 필요하고 복잡하다.
- **클래스 로딩 시점**: `java -javaagent`를 통해 클래스 로더 조작기를 지정해야 하는데, 번거롭고 운영하기 어렵다. (참고: 수많은 모니터링 툴들이 이 방식을 사용한다 — Java Instrumentation)
- **런타임 시점**: 프록시 방식이라 AOP 기능에 일부 **제약**이 있다. 하지만 특별한 컴파일러나 복잡한 옵션 없이 **스프링만 있으면** 된다.

### ⚠️ 프록시 방식의 제약 — 왜 메서드 실행으로 제한되는가

> **복습 세션에서 헷갈렸던 부분**: "빈 주입 이후에 사용 가능해서"라고 생각했지만, 근본 원인은 다르다.

**핵심: 프록시는 메서드 오버라이딩 개념으로 동작한다.**

```
클라이언트 → [프록시 객체] ──(메서드 호출 위임)──→ [타겟 객체]
                 ↑
           메서드 오버라이딩으로
           호출을 가로채는 구조
```

- 메서드 실행 → ✅ 오버라이딩으로 가로챌 수 있음
- 생성자 호출 → ❌ 오버라이딩 불가
- 필드 값 접근 → ❌ 오버라이딩 불가
- static 메서드 → ❌ 오버라이딩 불가

따라서:
- **스프링 AOP의 조인 포인트는 메서드 실행 지점으로 제한된다.**
- **스프링 컨테이너가 관리하는 스프링 빈에만** AOP를 적용할 수 있다.

AspectJ를 사용하면 바이트코드를 직접 조작하므로 생성자, 필드, static 메서드 등 모든 지점에 AOP를 적용할 수 있다.

## 3. 스프링 AOP vs AspectJ

### 왜 더 강력한 AspectJ를 두고 스프링 AOP를 쓰는가

| | 스프링 AOP | AspectJ |
|---|-----------|---------|
| 설정 | **스프링만 있으면 됨** | 특별한 컴파일러 + 전용 문법 + 자바 실행 옵션 |
| 적용 범위 | 메서드 실행만 | 생성자, 필드, static 등 모두 가능 |
| 실무 적합성 | **대부분의 문제 해결 가능** | 오버스펙인 경우가 많음 |
| 학습 비용 | 낮음 | 높음 |

### 스프링과 AspectJ의 관계

> **스프링은 AspectJ의 문법을 차용하고 프록시 방식의 AOP를 적용한다. AspectJ를 직접 사용하는 것이 아니다.**

- `@Aspect`, `@Around`, `execution(...)` 같은 **어노테이션과 포인트컷 표현식**은 AspectJ 것을 빌려 씀
- AspectJ의 **컴파일러, 로드타임 위버 등은 사용하지 않음**
- 내부적으로는 지금까지 배운 **프록시 방식**으로 AOP를 구현

## 4. AOP 용어 정리

### 용어 한눈에 보기

| 용어 | 의미 |
|------|------|
| **조인 포인트 (Join Point)** | 어드바이스가 적용될 수 있는 **모든 위치** — 메서드 실행, 생성자 호출, 필드 값 접근 등. **추상적인 개념**이다. 스프링 AOP에서는 프록시 방식이므로 **메서드 실행 지점으로 제한** |
| **포인트컷 (Pointcut)** | 조인 포인트 중에서 어드바이스가 적용될 위치를 **선별하는 기능(필터)**. 주로 AspectJ 표현식으로 지정 |
| **타겟 (Target)** | 어드바이스를 받는 **실제 대상 객체** = 프록시가 감싸고 있는 **진짜 객체**. 강의 원문은 "포인트컷으로 결정"이라고 덧붙이는데, 이는 **어떤 빈이 타겟이 될지를 선별하는 수단**이 포인트컷이라는 뜻 (아래 ⚠️ 참조) |
| **어드바이스 (Advice)** | 부가 기능 로직 그 자체. `Around`, `Before`, `After` 등 다양한 종류가 있음 |
| **애스펙트 (Aspect)** | 어드바이스 + 포인트컷을 **모듈화한 것**. `@Aspect`를 생각하면 됨. 여러 어드바이스와 포인트컷이 함께 존재 |
| **어드바이저 (Advisor)** | **하나의 어드바이스 + 하나의 포인트컷**으로 구성. 스프링 AOP에서만 사용되는 특별한 용어. [ProxyFactory](./proxy-factory.md)에서 최초 등장 |
| **위빙 (Weaving)** | 포인트컷으로 결정한 타겟의 조인 포인트에 어드바이스를 **적용하는 과정(동작)**, 그리고 그 결과로 애스펙트가 객체에 **연결된 상태**까지 가리킴. 위빙 덕분에 핵심 기능 코드에 영향을 주지 않고 부가 기능 추가 가능. 시점은 컴파일 타임 / 로드 타임 / 런타임(스프링) |
| **AOP 프록시** | AOP 기능을 구현하기 위해 만든 프록시 객체. 스프링에서는 JDK 동적 프록시 또는 CGLIB 프록시 |

### 조인 포인트와 포인트컷의 관계

```
전체 조인 포인트 (AOP 적용 가능한 모든 지점)
    │
    ├── orderController.request1()
    ├── orderController.request2()
    ├── orderService.order()        ← 포인트컷 매칭 ✅
    ├── orderService.change()       ← 포인트컷 매칭 ✅
    ├── orderRepository.save()      ← 포인트컷 매칭 ✅
    └── orderRepository.update()
    
    ↓ 포인트컷이 필터링
    
실제 어드바이스가 적용되는 지점 (order, change, save)
```

### ⚠️ 헷갈리기 쉬운 용어 구분

> **복습 세션에서 혼동한 부분들**

**타겟 ≠ "포인트컷 조건에 만족하는 객체"** — 정의와 선별 수단을 구분할 것
- 타겟의 **정체(정의)**는 프록시가 내부적으로 참조하고 있는 **원본 객체**
- 포인트컷은 그 타겟을 **선별하는 수단** — 강의 원문의 "포인트컷으로 결정"은 이 뜻이고, 둘은 모순이 아니다
- [ProxyFactory](./proxy-factory.md)에서 `new ProxyFactory(target)`으로 넘긴 그 객체가 바로 타겟
- "포인트컷 조건에 만족해서 프록시가 생긴 그 빈의 **원본 객체**"라고 하면 정확

**위빙 ≠ "적용되는 방식"**
- 위빙은 방식이 아니라 **적용하는 동작(행위)** 자체
- 컴파일 / 클래스 로딩 / 런타임은 위빙이 **일어나는 시점**

**애스펙트 vs 어드바이저**
- 어드바이저: 포인트컷 1 + 어드바이스 1 (항상 1:1, 가장 작은 단위)
- 애스펙트: 여러 포인트컷 + 여러 어드바이스를 묶는 **상위 개념**
- `AnnotationAwareAspectJAutoProxyCreator`가 @Aspect를 읽으면 **메서드 하나마다 어드바이저 하나로 분해**

```java
@Aspect
public class MyAspect {

    @Around("execution(* hello.order..*(..))")
    public Object doLog(ProceedingJoinPoint joinPoint) throws Throwable {
        // → 어드바이저 1개로 변환
        return joinPoint.proceed();
    }

    @Before("execution(* hello.service..*(..))")
    public void doValidation(JoinPoint joinPoint) {
        // → 어드바이저 1개로 변환
    }
}
// 결과: 스프링 내부에서 어드바이저 2개가 생성됨
```

## 5. Ch.4~9 발전사 연결 — 전체 동작 흐름

이번 챕터에서 배운 AOP 개념이 Ch.4~8의 기술들과 어떻게 연결되는지 정리한다.

### 전체 흐름

```
[빈 등록 시점]
@Aspect 클래스가 스프링 빈으로 등록
    → AnnotationAwareAspectJAutoProxyCreator가 읽음 (Ch.8)
    → 내부적으로 어드바이저(Advisor)로 변환·캐싱

[다른 빈 생성 시점]
빈 생성
    → 빈 후처리기(BeanPostProcessor)가 postProcessAfterInitialization에서 개입 (Ch.7)
    → 등록된 모든 어드바이저의 포인트컷으로 해당 빈 체크
       (클래스 정보 + **모든 메서드를 하나하나 매칭** — 메서드 하나만 조건에 만족해도 프록시 적용 대상)
    → 적용할 어드바이저가 하나라도 있으면
        → ProxyFactory로 프록시 생성 (Ch.6)
            → 인터페이스 있으면 JDK 동적 프록시, 없으면 CGLIB (Ch.5)
            → Spring Boot는 proxyTargetClass=true 기본 → 항상 CGLIB
        → 실제 빈 대신 프록시를 스프링 컨테이너에 등록

[런타임 — 메서드 호출 시점]
클라이언트 → 프록시.method()
    → 포인트컷으로 해당 메서드 매칭 체크
    → 매칭되면 어드바이스 실행 → 타겟의 실제 메서드 호출
    → 매칭 안 되면 타겟 메서드 직접 호출
```

### ⚠️ 포인트컷 체크가 두 번 일어난다

[빈 후처리기](./bean-post-processor.md)에서 이미 배운 내용이지만, AOP 용어와 연결하면:

1. **빈 생성 시 (클래스 레벨)**: 이 빈에 프록시를 **만들지 말지** 판단
2. **런타임 시 (메서드 레벨)**: 이 메서드에 어드바이스를 **적용할지** 판단

---

## 💡 판단 기준

**"AspectJ를 직접 써야 하나?"라는 질문이 나오면** — 거의 대부분 NO다. 스프링 AOP가 제공하는 메서드 실행 지점 AOP만으로 실무의 대부분의 문제(트랜잭션, 로그, 보안, 캐시)가 해결된다. 특별한 컴파일러와 복잡한 설정이라는 비용을 감수할 만큼 생성자·필드 접근에 AOP가 필요한 경우는 극히 드물다. "스프링 AOP로 안 되는 것"을 만나기 전까지는 고민할 필요 없다.

**이 챕터의 본질**: Ch.4~8이 "어떻게(How)"를 배운 거라면, Ch.9는 "왜(Why)"를 배운 챕터다. AOP라는 패러다임이 해결하려는 **문제**를 이해하고, 그 문제를 풀기 위해 등장한 **용어 체계**를 정확히 잡는 것이 핵심이다. 여기서 용어가 흔들리면 Ch.10~13에서 계속 혼동이 생긴다.
