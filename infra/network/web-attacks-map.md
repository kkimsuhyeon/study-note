# 웹 공격 지도 — 쿠키(출입 카드)를 중심으로 한 다섯 가지 공격과 막는 장치

> **한 줄 요약:** 브라우저의 쿠키는 그 사이트의 **출입 카드**다. 대표적인 웹 공격은 이 카드를 **훔치거나**(세션 탈취), 카드를 가진 브라우저를 **속여서 대신 일하게 하거나**(CSRF), 아예 **우리 페이지 안에 숨어들거나**(XSS), 화면을 덮어 **잘못 누르게 하거나**(클릭재킹), 문을 **계속 두드리는**(남용) 것이다. 공격마다 막는 장치가 다르고, 장치끼리 서로를 대신하지 못한다.

## 먼저 기본 그림

- 사용자가 사이트를 쓰면 서버가 쿠키를 준다. 브라우저는 그 사이트로 요청할 때마다 쿠키를 **자동으로** 붙인다.
- 서버는 쿠키만 보고 "아, 그 사람이구나"라고 판단한다. 요청을 **누가 어디서 만들었는지**는 쿠키만으로는 모른다.
- 이 두 성질(자동으로 붙는다, 쿠키만 보고 판단한다)이 대부분의 공격이 노리는 지점이다.

## 공격 다섯 가지

### 1. 세션 탈취 — 출입 카드를 훔친다

- **무엇**: 공격자가 쿠키 **값 자체**를 손에 넣어 Postman 같은 도구로 직접 붙여 보낸다. 서버는 진짜 사용자와 구분하지 못한다.
- **훔치는 길과 막는 장치**:

  | 훔치는 길 | 막는 장치 |
  | --- | --- |
  | 페이지에 심은 스크립트가 `document.cookie`로 읽기 | `HttpOnly` — 자바스크립트가 쿠키를 못 읽게 |
  | 암호화 안 된 네트워크에서 엿보기 | `Secure` + HTTPS — 암호화된 연결로만 보내게 |
  | URL·로그에 남은 값 줍기 | 세션 ID를 URL·로그에 남기지 않기 |
  | 피해자 기기에 접근(개발자 도구·악성 확장·악성코드) | 서버로는 못 막는다. 만료 시간으로 피해를 줄인다 |

### 2. CSRF — 카드를 가진 브라우저를 속여 대신 보내게 한다

- **무엇**: 사용자가 악성 사이트에 들어가면, 그 페이지가 몰래 우리 사이트로 요청을 보낸다. 브라우저는 쿠키를 자동으로 붙이고, 서버는 본인 요청으로 착각한다. 공격자는 **쿠키 값을 한 번도 보지 않는다.**
- **막는 장치**(겹쳐 쓴다):

  | 장치 | 하는 일 |
  | --- | --- |
  | `SameSite=Lax` 쿠키 | 다른 사이트에서 시작된 POST에는 브라우저가 쿠키를 **안 붙인다** |
  | Origin 검사 | 브라우저가 붙이는 "출발한 페이지 주소"(Origin)를 보고 남의 사이트면 거절 |
  | JSON만 받기 | 다른 사이트가 JSON을 보내려면 브라우저가 허락(preflight)을 먼저 구하는데, 허락하지 않으면 요청 자체가 안 나간다. 폼은 JSON을 못 보낸다 |
  | CSRF 토큰 | 우리 페이지에만 준 난수를 요청에 다시 실어 보내게 한다. 남의 사이트는 그 값을 모른다 |

- `HttpOnly`는 CSRF를 **못 막는다.** 읽기만 막고, 브라우저가 붙여 보내는 건 막지 않기 때문이다.
- CSRF 토큰은 **로그인 토큰이 아니다.** 로그인 토큰은 "누구냐", CSRF 토큰은 "우리 화면에서 만든 요청이냐"를 증명한다.

### 3. XSS — 우리 페이지 안에 숨어든다

- **무엇**: 공격자가 넣은 글(이름, 댓글, AI 출력)이 화면에 그려질 때 스크립트로 실행된다. 그 스크립트는 **우리 페이지 안에서** 돌기 때문에, 우리 사이트로 보내는 요청이 전부 정상처럼 보인다.
- **가장 위험한 이유**: 안에 들어오면 CSRF 방어(Origin·SameSite·토큰)가 전부 통과된다. 쿠키 값을 못 읽어도 쿠키로 요청은 보낼 수 있다.
- **막는 장치**:

  | 장치 | 하는 일 |
  | --- | --- |
  | 출력 이스케이프 | 글을 화면에 **글자로** 그린다(React `{}`는 기본). HTML로 그리는 곳(`dangerouslySetInnerHTML`, 마크다운 변환)이 구멍 |
  | CSP 헤더 | 허락한 스크립트만 실행되게 브라우저에 지시. 이스케이프를 한 곳에서 실수해도 버틴다 |
  | 입력 규칙 | 허용 문자를 줄여 표면을 줄인다. 단 출력 이스케이프의 대체는 아니다 |

### 4. 클릭재킹 — 화면을 덮어 잘못 누르게 한다

- **무엇**: 악성 사이트가 우리 페이지를 투명한 `<iframe>`으로 깔고 그 위에 "경품 받기" 버튼을 그린다. 사용자는 경품 버튼을 누르지만 실제로는 아래의 "삭제" 버튼을 누른다.
- **막는 장치**: 우리 페이지가 남의 사이트 iframe 안에 들어가지 못하게 한다 — CSP `frame-ancestors 'none'` 또는 `X-Frame-Options: DENY` 헤더. HTML 페이지를 내려 주는 쪽에 건다.

### 5. 남용 — 문을 계속 두드린다

- **무엇**: 스크립트로 요청을 대량으로 보내 비용(AI 호출 등)을 쓰게 하거나 서비스를 느리게 만든다. 사용자를 속이는 공격이 아니라 **서버를 직접** 노린다.
- **막는 장치**: 요청 횟수 제한([Rate Limiting](../rate-limiting.md)). 쿠키는 지우면 새로 생기므로 세션 기준 하나로는 부족하고 IP 기준을 함께 건다.

## 한 장 요약

| 공격 | 공격자가 하는 일 | 막는 장치 |
| --- | --- | --- |
| 세션 탈취 | 카드를 훔쳐 직접 씀 | HttpOnly, Secure, 로그·URL에 안 남김, 만료 |
| CSRF | 브라우저를 속여 대신 보내게 함 | SameSite, Origin 검사, JSON 전용, CSRF 토큰 |
| XSS | 우리 페이지 안에서 스크립트 실행 | 출력 이스케이프, CSP |
| 클릭재킹 | 투명하게 덮어 클릭 유도 | frame-ancestors, X-Frame-Options |
| 남용 | 대량 요청 | 횟수 제한 |

## 자주 묻는 것

**카드는 정확히 무엇인가?** 서버가 사람을 알아보는 데 쓰는 쿠키다. 서버 세션 방식이면 **세션 ID 쿠키**(`SESSION`, `JSESSIONID`), JWT를 쿠키에 담는 방식이면 그 JWT 쿠키. 세션 안에 든 값(소유자 식별값 등)은 카드가 아니라 카드로 여는 **사물함 안의 물건**이다.

**세션은 페이지별인가, 브라우저별인가?** 쿠키는 **브라우저 프로필 하나**에 사이트별로 저장된다. 같은 프로필의 탭·창은 모두 같은 쿠키를 쓰므로 같은 세션이다.

| 상황 | 세션 |
| --- | --- |
| 같은 크롬에서 탭·창을 새로 염 | 같음 |
| 크롬을 껐다 켬 | 쿠키에 보관 기간(`Max-Age`)이 있으면 같음. 없으면 꺼질 때 사라질 수 있음 |
| 시크릿 창 | 다름. 시크릿 창끼리는 열려 있는 동안 서로 공유하고(크롬 기준), 모두 닫으면 사라짐 |
| 다른 크롬 프로필·다른 브라우저·다른 기기 | 다름 |
| 쿠키 삭제 | 새 세션 |

**b.com이 a.com에서 보낸 것처럼 속일 수 없나?** 브라우저 안에서는 못 한다. Origin 헤더도, SameSite 판단도 **브라우저가** 실제로 요청을 시작한 페이지를 보고 정하고, 자바스크립트는 그 값을 바꿀 수 없다. curl 같은 브라우저 밖 도구로는 `Origin: https://a.com`을 마음대로 적을 수 있지만, 그 도구에는 **피해자의 쿠키가 없다.** 정리하면 "속이려면 피해자의 브라우저가 필요한데, 피해자의 브라우저는 거짓말을 하지 않는다." 예외는 공격자가 실제로 a.com 안(XSS)이나 같은 사이트의 서브도메인에 들어와 있을 때인데, 그건 속이는 게 아니라 정말 거기 있는 것이다.

**SameSite가 카드를 안 붙이면 요청은 막히나?** 막히지 않는다. 요청은 서버에 **도착하고**, 쿠키만 빠져 있다. 서버는 "모르는 사람의 요청"으로 처리한다 — 로그인이 필요한 기능이면 401, 익명 서비스면 새 방문자. 피해자의 신분이 실리지 않으니 피해자 이름으로는 아무것도 못 한다. 정리하면 **SameSite는 신분을 떼어 내고, Origin 검사는 문 앞에서 돌려보낸다.**

**CSRF 토큰은 어떻게 동작하나? 브라우저는 아는데 남의 사이트는 모른다는 게 무슨 뜻인가?**

1. 우리 페이지가 열릴 때 서버가 토큰(난수)을 준다. 페이지 안에 넣어 주거나, 우리 자바스크립트가 읽을 수 있는 쿠키(`XSRF-TOKEN`)로 준다.
2. 우리 페이지의 자바스크립트가 그 값을 읽어 요청 **헤더**(`X-XSRF-TOKEN`)에 **직접 적어서** 보낸다.
3. 서버는 헤더의 값이 기대한 값과 같은지 비교한다.

악성 사이트가 요청을 보내면 브라우저는 쿠키는 **자동으로** 붙이지만, 헤더는 **스크립트가 직접 적어야** 한다. 그런데 브라우저에는 **동일 출처 정책**이라는 기본 규칙이 있다 — 한 사이트의 스크립트는 다른 사이트의 쿠키나 페이지 내용을 읽지 못한다. 그래서 악성 사이트 스크립트는 토큰 값을 알 수 없고, 헤더에 맞는 값을 적지 못한다. "브라우저는 알고 있다"는 건 브라우저가 값을 **보관**한다는 뜻이고, "남의 사이트는 모른다"는 건 남의 사이트 스크립트가 그 값을 **꺼내 볼 수 없다**는 뜻이다. 비유하면 출입 카드(쿠키)는 브라우저가 자동으로 내밀지만, 비밀번호(토큰)는 입력창에 직접 쳐야 하고, 그 비밀번호는 우리 화면에만 적혀 있다.

## ⚠️ 헷갈리는 것

- **CORS는 공격이 아니다.** 다른 사이트에 "우리 응답을 읽어도 된다"고 **허락**하는 장치다. 켜면 문이 열리는 쪽이다([Origin 헤더](./origin-header.md)).
- **장치는 서로를 대신하지 못한다.** HttpOnly는 CSRF를 못 막고, Origin 검사는 훔친 쿠키를 못 막고, CSRF 방어는 XSS가 뚫리면 무력하다.
- **"토큰"이라는 말이 두 번 나온다.** 로그인 토큰(누구냐)과 CSRF 토큰(우리 화면에서 만든 요청이냐)은 다른 것이다.

## 💡 판단 기준

새 기능을 만들 때 다섯 질문을 차례로 던진다. ① 이 값이 새면 남이 나로 행세할 수 있나(탈취) ② 남의 사이트가 내 브라우저로 이 요청을 보낼 수 있나(CSRF) ③ 이 입력이 화면에 HTML로 그려질 수 있나(XSS) ④ 이 화면이 남의 사이트 안에 들어갈 수 있나(클릭재킹) ⑤ 이걸 1초에 천 번 부르면 무슨 일이 나나(남용).
