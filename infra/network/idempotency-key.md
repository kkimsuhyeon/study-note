# 중복 요청과 멱등 키 — 어떤 API에 키가 필요한가

> **한 줄 요약**: "같은 요청이 두 번 와도 결과가 한 번과 같아야 한다"(멱등성)는 모든 API의 요구지만, **멱등 키가 필요한 API는 일부다.** 조회는 원래 안전하고, "값을 X로 설정"은 몇 번 해도 같고, "상태가 A일 때만 B로"는 상태가 두 번째를 막아 준다. 키가 꼭 필요한 건 **서버 상태만으로는 중복인지 구분할 수 없는 쓰기** — 누적(충전 +10원)과 새로 만들기(주문 생성)다.

## 언제 쓰나

- 클라이언트가 타임아웃·네트워크 오류 뒤 **재전송**할 수 있는 쓰기 API (모바일 앱, 결제 연동, 외부 시스템 연동)
- 버튼 두 번 클릭, 프록시·HTTP 클라이언트의 자동 재시도가 있을 수 있는 곳
- 같은 요청이 두 번 실행되면 **돈·재고·포인트가 두 번 움직이는** 기능

## 판단 기준 — "두 번 실행되면 결과가 달라지나?" → "서버가 중복을 알아챌 수 있나?"

| 요청 종류 | 예 | 두 번 오면 | 막는 방법 |
|---|---|---|---|
| 조회 | 잔액 조회, 좌석 목록 | 아무것도 안 바뀜 | 필요 없음 |
| 값 설정 (덮어쓰기) | 이름을 "김철수"로 변경, 삭제 | 같은 결과 | 필요 없음 (HTTP `PUT`·`DELETE`가 멱등으로 정의된 이유) |
| 상태 전이 (조건부) | 좌석 AVAILABLE → RESERVING, 예약 PENDING → CONFIRMED | 두 번째는 상태 검사에서 실패 | **상태 + 락**으로 막힘. 키는 선택(두 번째 요청에도 "성공" 응답을 주고 싶을 때) |
| 자연 키가 있는 생성 | 같은 이메일로 회원가입, 사용자당 대기열 토큰 1개 | 유니크 제약·"이미 있으면 그것 반환" | 자연 키 + 유니크 제약 |
| **누적 변경** | 포인트 충전 +10원 | **20원이 됨** — 서버는 "일부러 두 번"인지 "재전송"인지 모름 | **멱등 키 필요** |
| **식별자 없는 생성** | 주문 생성, 보고서 생성 | **두 개가 생김** | **멱등 키 필요** |

- HTTP 의미로는 `GET`·`HEAD`·`PUT`·`DELETE` 등이 멱등 메서드다(RFC 9110 §9.2.2). `POST`·`PATCH`는 멱등이 보장되지 않는다. 다만 메서드는 약속일 뿐이라, 실제 구현이 지키는지는 위 표처럼 따로 따진다.
- 동시성(서로 다른 요청이 동시에 와서 갱신이 사라짐)과 멱등성(같은 요청이 두 번 실행됨)은 **다른 문제**다. 락은 동시성을 막지만, 두 번째 요청이 락을 기다렸다가 다시 +10원을 하는 것까지 막지는 못한다.

## 멱등 키 처리 흐름

```text
클라이언트: 요청마다 고유 키 생성(UUID) → Idempotency-Key 헤더로 전송 → 재전송할 땐 같은 키
서버:
  ① 키 형식 검사 (없거나 형식이 틀리면 400)
  ② 요청 내용 지문 계산 (본문 해시)
  ③ 같은 (주체, 키) 요청을 한 줄로 세움 (락)
  ④ 키 기록 조회
       있음 + 지문 같음   → 실행하지 않고 이전 결과 반환
       있음 + 지문 다름   → 오류 (같은 키를 다른 요청에 재사용)
       없음              → 실제 작업 실행 + 키 기록 저장
  ⑤ ③~④를 한 트랜잭션으로 — 작업과 키 기록이 같이 커밋되거나 같이 롤백
```

IETF 초안 `Idempotency-Key` 헤더(draft-ietf-httpapi-idempotency-key-header, 아직 RFC 아님)가 권하는 응답:

| 상황 | 권장 상태 코드 |
|---|---|
| 키가 필요한 API인데 키 없음 | 400 |
| 같은 키를 다른 내용으로 재사용 | 422 |
| 같은 키의 첫 요청이 아직 처리 중 | 409 |

③에서 기다리게 하면(첫 요청이 끝난 뒤 이전 결과 반환) 409 대신 성공을 줄 수도 있다. 어느 쪽이든 문서에 적어 둔다.

## ③ "한 줄로 세우기"를 무엇으로 하나

| 방법 | 언제 | 주의 |
|---|---|---|
| **이미 있는 행의 락** (`SELECT ... FOR UPDATE`) | 작업 대상 행이 이미 있을 때 — 예: 충전은 사용자 행을 어차피 잠근다 | **락을 잡은 뒤에** 키를 조회해야 한다. 먼저 조회하면 두 요청이 동시에 "기록 없음"을 본다 |
| advisory lock (PostgreSQL) | 잠글 행이 **아직 없을 때** — 새로 만드는 요청 | 상세 → [PostgreSQL Advisory Lock](../../database/postgres-advisory-lock.md) |
| 유니크 제약에 먼저 넣기 | 키 행을 먼저 INSERT, 중복이면 기존 결과 조회 | MySQL InnoDB는 중복 오류 시 그 문장만 되돌린다. 하지만 **JPA/Hibernate는 제약 위반 예외가 나면 그 트랜잭션을 롤백 전용으로 만들고 영속성 컨텍스트를 더 쓸 수 없게 된다** — 별도 트랜잭션이나 네이티브 쿼리로 처리해야 한다 |
| Redis 분산락 | 서버가 여러 대이고 Redis가 이미 있을 때 | 락 해제와 DB 커밋 순서 |

## 재전송에 무엇을 돌려주나 — 키 기록의 "결과" 칸

| 방법 | 기록에 남기는 것 | 재전송 응답 | 비용 |
|---|---|---|---|
| A. 결과 없음 | 키·종류·지문만 | "성공"만 다시 | 돌려줄 본문이 있는 API엔 부족 |
| B. 결과 아이디 | 만들어진 행의 id (특정 테이블 FK면 그 기능 전용 장부가 됨) | 그 id로 **현재** 상태를 조회해 응답 | FK 없이 두면 다용도지만 무결성·정리는 직접 |
| C. 응답 통째로 | 상태 코드 + 본문 | **처음 응답 그대로** — 업무 로직을 다시 돌리지 않음 | 저장량, 응답 속 민감 정보까지 저장 |

C의 대표 사례가 Stripe다. 공식 API 문서(2026-10-21 확인) 기준 API v1은 **엔드포인트 실행이 시작된 뒤 첫 요청의 상태 코드와 본문을 저장하고, 같은 키의 재시도에는 저장된 응답을 그대로 돌려준다 — 500 오류까지 포함해서.** 들어온 파라미터가 처음 요청과 다르면 오류를 내고, 키는 24시간 이상 지나면 정리될 수 있다. 반면 API v2는 실패했거나 일부만 된 작업을 가능하면 끝까지 다시 시도한다 — 같은 회사 안에서도 "실패를 저장해 돌려줄지, 다시 시도할지"가 갈린다.

B와 C의 차이는 **재전송 시점에 상태가 바뀌었을 때** 드러난다. 충전 직후 다른 결제로 잔액이 줄었다면, B는 지금 잔액을, C는 충전 직후 잔액을 돌려준다. "내 요청의 결과"를 보여 주는 게 목적이면 C, "지금 상태"를 보여 주면 되면 B.

작업과 키 기록을 한 DB 트랜잭션에 넣는 구현에서는 C의 응답도 **같은 트랜잭션 안에서** 만들어 저장해야 한다. 그래서 HTTP 응답 객체가 아니라 유스케이스의 결과 객체를 직렬화해 두고, 재전송이면 그 결과로 같은 HTTP 응답을 다시 만드는 편이 계층을 섞지 않는다. 이 구현에서 실패는 롤백되어 기록이 남지 않으므로 "실패도 저장"하는 Stripe v1과 동작이 다르다(재시도하면 다시 실행된다).

## ⚠️ 함정

- **키를 서버가 만들면 의미가 없다.** 재전송을 알아보는 정보는 클라이언트만 갖고 있다. 서버가 요청마다 새 키를 만들면 매번 다른 요청이 된다.
- **키만 보고 내용을 안 보면** 같은 키로 금액만 바꾼 요청을 "이전과 같은 요청"으로 착각해 엉뚱한 결과를 돌려준다 → 지문 비교.
- **실패한 요청도 기록할지** 정해야 한다. 잔액 부족처럼 다시 보내도 같은 실패가 나는 오류는 기록해도 되지만, 일시 장애(타임아웃)는 기록하면 재시도가 영원히 실패한다. 작업과 키 기록을 한 트랜잭션에 두면, 실패 시 둘 다 롤백되어 자연스럽게 "기록 없음"이 된다.
- **키 보관 기간.** 영원히 쌓이므로 보관 기간을 정하고 지운다(재전송이 일어날 만한 기간보다 길게).
- **주체별로 묶는다.** 키 PK를 (사용자, 키)로 두지 않으면 다른 사람의 키와 충돌하거나 남의 결과를 받을 수 있다.

## 💡 판단 기준

**API를 만들 때 "이 요청이 두 번 실행되면 무엇이 두 번 움직이나?"를 먼저 묻는다.** 아무것도 안 움직이면(조회·덮어쓰기) 끝, 상태가 두 번째를 막으면 상태+락으로 충분, **돈·수량이 누적되거나 새 행이 생기는데 서버가 중복을 구분할 정보가 없을 때만** 멱등 키를 붙인다. 포인트 충전이 키가 필요한 대표 사례이고, 좌석 예약·결제는 상태 전이로 대부분 막힌다(그래도 "재전송에 같은 성공 응답"이 필요하면 키를 쓴다).
